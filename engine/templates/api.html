API & data

Catalog endpoints and mapping rules

Everything on this site is generated from two committed, validated catalogs: software from endoflife.date and hardware from eosl.date together with Opengear's own end-of-life product list. The JSON below is the same data the pages render — no private fields, no server, no API keys.

Endpoints

Software catalog

  • {{ feed_url|replace(base_path, '') }} Full normalized catalog. Top-level fields: schema_version ({{ schema_version }}), generated_at, source_url, product_count, release_count, excluded_hardware, and products — every product record, complete.
  • {{ products_url|replace(base_path, '') }} Index of summaries: counts, per-milestone coverage, the newest release, the next published deadline, and the absolute URL of each product endpoint.
  • v1/products/{{ sample_product }}.json One product record, byte-identical to the file committed under data/products/. Replace the id in the path with any id from the index.

Hardware catalog

  • {{ hardware_url|replace(base_path, '') }} Index of hardware summaries. Each entry carries id, name, vendor, status (supported, expiring, eol or the neutral unknown), per-milestone coverage, the normalized milestones, the next published deadline, and the absolute URL of that record's endpoint. One entry is one published source row: a model or model group from eosl.date, an Opengear product group, or one exact Opengear catalogue model. status: unknown is not a synonym for supported — it means the record carries no support deadline and no matching notice, so no claim is made either way. hardware_count in the catalog manifest matches the array length, and it counts records, not devices or SKUs.
  • v1/hardware/{{ sample_hardware }}.json One hardware record, byte-identical to the file committed under data/hardware/. Replace the id in the path with any id from the hardware index.
  • record.catalog and record.lifecycle — optional, present on exact catalog models: A record whose family is catalog is one exact vendor model string from Opengear's product catalogue. Its id is stable: an id is never re-minted when a notice later names the model. catalog is {listed, source_url}, where listed is current presence in the catalogue and source_url is {{ catalog_source_site }}. lifecycle is {listed, matches}, where matches holds the ids of the published lifecycle records whose notice names this exact model string — matched on the notice's Part # scope only, never its replacement column, never a substring, never a family — and listed is true exactly when a notice resolves. Neither field is a support claim: a catalog listing is not an entitlement, its disappearance is not an end of sale, a revision-only notice never retires a whole model, and a matching notice's dates belong to the linked record.
  • v1/opengear-import.json Import report for the Opengear source: the counts parsed, imported and excluded, and every excluded row with its product, table and reason. Rows from Opengear's software tables, and rows whose support state the source does not state, are excluded here rather than published as hardware records.

Examples

No authentication, no parameters. All examples are read-only GET requests.

List products with the soonest published deadline

curl -s {{ products_abs }} \
  | jq '.products | sort_by(.next.date // "9999") | .[:5] | .[] | {id, name, next}'

Fetch one product record

curl -s {{ site_url('v1/products/' ~ sample_product ~ '.json') }} \
  | jq '{id, name, releases: [.releases[] | {id, ga: .milestones.ga, eol: .milestones.eol}]}'

List hardware records past end of support, by vendor

curl -s {{ hardware_abs }} \
  | jq '[.hardware[] | select(.status == "eol")] | group_by(.vendor)
        | map({vendor: .[0].vendor, records: length}) | sort_by(-.records)'

Fetch one hardware record and its raw upstream cells

curl -s {{ site_url('v1/hardware/' ~ sample_hardware ~ '.json') }} \
  | jq '{id, vendor, model: .model_number, milestones, sources: .provenance.source_urls}'

Filter the full feed to records with a published end of life

curl -s {{ feed_abs }} \
  | jq '[.products[] | select(any(.releases[]; .milestones.eol != null)) | .id]'

Check the raw upstream value behind a normalized date

curl -s {{ site_url('v1/products/' ~ sample_product ~ '.json') }} \
  | jq '[.releases[] | {id, normalized: .milestones.eossec, raw: {eolFrom: .upstream.eolFrom, label: null}}][:3]'

Software record shape

id
Product slug. Also the filename under data/products/ and the path segment of its endpoint.
name
Display name from upstream label.
category
Always software in this catalog; hardware has its own catalog and endpoint.
upstream_category
Upstream endoflife.date category (app, database, framework, lang, os, server-app, service, standard), kept unmodified.
identifiers
Upstream identifiers such as CPE values, verbatim.
labels
The product's upstream label object, used to interpret the raw date fields.
links
Upstream link object (icon, release policy, and so on), verbatim.
releases[].id
The upstream release name, used as the release key.
releases[].name
Display label for the release.
releases[].milestones
The four normalized dates: ga, eos, eossec, eol. Each is an ISO date or null; null means upstream publishes no date, never a guessed one.
releases[].upstream
The entire original upstream release object, so any normalized value can be audited against its source.
provenance
source_url, verifier (pipeline revision), last_checked (UTC, per record), upstream_modified (or null when upstream publishes none).

Hardware record shape

id
Model slug. Also the filename under data/hardware/ and the path segment of its endpoint.
name
The product name the record's source publishes for the row.
category
Always hardware.
vendor
The vendor the source attributes the record to: the family page's vendor from its URL and breadcrumb, or Opengear for its own product table.
product_line
The vendor's product line for the record, or the vendor name when the source publishes none.
family, model_number
The source family and model number, verbatim. An Opengear lifecycle row groups a whole product's part numbers, so model_number is the first published part number and the full list stays verbatim in upstream. A catalog record's family is catalog and its model_number is the single exact vendor model string, reproduced without folding, splitting or reordering.
milestones
The four normalized dates: ga, eos, eossec, eol. Each is an ISO date or null, and null means the record's source publishes no such date. eossec is always null, and ga is null for every Opengear record: neither source publishes a security-support or General-availability column for hardware. All four are null on a catalog record, which has no notice of its own; a notice's dates live on the lifecycle record it matches.
status
supported, expiring, eol, or unknown. For eosl.date records this is the row the source publishes the model under; for Opengear lifecycle rows it is computed from the published support deadline against the import date, because that source states no row status. unknown is the honest value for a record with no deadline and no matching notice — it is not a synonym for supported, and a catalog listing never produces a dated status.
upstream
Every declared column of the source row, verbatim: text as rendered, datetime and value for a machine-readable date or null, the milestone role the pipeline assigns (or null), and any links. For an Opengear record this also carries the source's own notes: the raw policy or contract-exception text, and the documented grouping semantics of the row. A catalog record's cells are keyed by the configurator's own field names (SKU, Title, Support Series, Families, Datasheet URL, and so on) and carry no milestone role.
catalog, lifecycle
Optional, and present only on exact catalog models. catalog is {listed, source_url} and lifecycle is {listed, matches}; see the catalog model entry under Endpoints for exactly what each states and what it deliberately does not.
provenance
source_urls (every page the record was read from), verifier (deterministic-eosl-date or deterministic-opengear, one per record, naming the pipeline that parsed it) and last_checked (UTC). A catalog record's source_urls lead with {{ catalog_source_site }}, the page it was read from, with any notice page that later named it appended rather than substituted.

A hardware record is one published source row, not a family of releases, so there is no releases array: its milestones describe the record itself. An eosl.date row is one model or model group; an Opengear lifecycle row is a product group whose part numbers are grouped rather than expanded into one record per part; a catalog record is one exact model string the vendor's product catalogue currently lists or listed. Record counts count records, never unique devices or SKUs.

Upstream mapping

The normalization is deliberately conservative. A label that does not qualify a field never turns that field into a deadline, and every raw value stays in the record whether or not it was mapped.

Software (endoflife.date)

MilestoneUpstream inputRule
General availability releaseDate Used as is whenever present. A boolean upstream status is never treated as a date.
End of sale eoasFrom, discontinuedFrom Only when the matching label (eoas, discontinued) names an end of sale. discontinued alone implies no end-of-sale date.
End of security support eolFrom, eoesFrom eolFrom when its label names security support. When the eoes label names security support, its date supersedes eolFrom even if the date is unknown.
End of life eoesFrom, else eolFrom A published extended-support date wins. Otherwise eolFrom is used only when no extended-support label is set and the eol label describes a full support end. An unknown extension leaves this null.

Consequence for readers: a null end of life can mean either that no support end was published, or that an announced extension has no published end date. Both cases keep the raw eolFrom value visible on the product page, so the earlier published deadline is never hidden.

Hardware — eosl.date only

The table below describes the eosl.date pipeline (deterministic-eosl-date) alone. Hardware columns are read by role, not by position: the source declares every header, and a column is matched to a milestone case- and whitespace-insensitively. Anything that matches no role stays in upstream untouched.

MilestoneSource columnsRule
General availability Release Date, Launch Date The rendered date, or the <time datetime> value when the cell carries one.
End of sale End of Sale Date, End of Sales Date, End of Life Date eosl.date's own glossary defines its end-of-life-date column as the end of sales date, so that column maps here and never to end of support.
End of security support none eosl.date publishes no security-support column, so this milestone is always null for its records rather than borrowed from another column.
End of support End of Support, End of Support (EOSL), End of Support Date, End of Service, End of Service Date The terminal support column — eosl.date's EOSL/LDOS. Relative prose rendered beside the date is stripped; a cell holding no date (a sentinel such as TBD, or a support URL) yields null.

Columns such as EOL Announced, the day-support and warranty discontinuance columns, and Version Number state no milestone of their own, so they are published verbatim in upstream and never promoted into a date. A model appearing in several families merges on its identity; milestones only ever gain a value, and two sources disagreeing on one date is an error to fix, not a tie to break.

Hardware — Opengear only

Opengear records (deterministic-opengear) are read from Opengear's own lifecycle tables. Columns are matched to a milestone by their exact declared header; the two tables below are the only shapes the pipeline accepts, and a missing, renamed or empty table fails the import rather than publishing a partial row.

Source tableMilestoneSource columnsRule
Hardware Lifecycle End of sale End of Sale Mapped to eos. The row's Product, Part #, Replacement Product and Note columns state no milestone and stay verbatim in upstream.
Hardware Lifecycle End of support End of Support Mapped to eol: the published support deadline for the product group.
Hardware Revisions End of sale Old Part Sales End Mapped to eos for the old part the revision row names.
Hardware Revisions End of support Old Part Support Ends Mapped to eol for that old part. Its Product, Old Part / Rev #, New Part / Rev # and Note columns stay verbatim in upstream.

Two consequences for consumers. No Opengear column feeds ga or eossec: Opengear publishes neither a first-availability nor a security-only deadline, so both are always null on its records — as eossec is on every hardware record. And rows are grouped: one record per published product group (for example a chassis product with all of its SKUs, or an old part with the revision that supersedes it), not one record per part number. The SKU and part lists stay verbatim in upstream. Opengear's own policy and contract-exception text is likewise retained raw in upstream and never converted into a date; the computed status does not override such a contract.

Opengear's software and subscription tables are not hardware lifecycle data and are excluded, as are rows whose support state the source does not state. Every excluded row is reported with its product, table and reason in v1/opengear-import.json (listed under Endpoints) rather than being published as a record.

Hardware — Opengear product catalog

Opengear's product configurator ({{ catalog_source_site }}) is read for a different question than the lifecycle tables: which exact models the vendor currently lists. Each listed model becomes one record with family: catalog, its name and model_number set to the vendor's own model string and its raw configurator fields kept verbatim in upstream. No date is read from the catalogue, because it publishes none.

FieldSourceRule
Record scope Configurator model list One record per exact model string. A model string is never split on hyphens, folded, title-cased or expanded into option combinations, and two catalogue entries that differ only in case remain two records rather than one.
Record identity Model string Derived from the model string alone, so the record keeps its id and its URL when the catalogue drops it and when a notice later names it. A notice never renames or re-mints a catalogue record.
catalog.listed Current configurator listing true while the catalogue lists the model, false once it is gone. The record is retained either way; nothing is deleted for disappearing, and no date is invented from the disappearance.
lifecycle.matches Notice Part # cell Ids of published lifecycle records whose notice scope contains this exact model string. Comparison is exact equality in both directions: the replacement-product column is never consulted, a substring or prefix is never a match, and a product family is never expanded into its members.
Revision notices Notice Old Part / Rev # rows A revision row names a revision, not a whole model, so it never matches a catalogue model and never implies that the model's whole SKU range is retired.
Several matches Multiple notice records Every matching record is published as a separate link. The site never picks one, never merges the dates and never invents a precedence order, so a consumer sees the disagreement instead of a resolution the source does not state.

Consequences worth stating plainly: catalogue presence is not support entitlement, catalogue disappearance is not end of life, and a catalogue record with no matching notice carries status: unknown rather than a borrowed status or a guessed date. Where a notice does match, its dates stay on the lifecycle record and the catalogue record links to it.
